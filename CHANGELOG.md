# Changelog

All notable changes to fLLM are documented in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project aims to follow [Semantic Versioning](https://semver.org/) once it leaves the 0.x series (0.x releases may change
behaviour between versions).

## [Unreleased]

### Added (checkpoint formats)
- **More quantized checkpoint formats are read** (all expanded to F16 by `convert` / direct load; each checked against the producing library on tiny synthetic checkpoints, see `docs/model-coverage.md`): compressed-tensors integer weights with zero points (asymmetric, 1-8 bits, compressed-tensors 0.20.1) and with `weight_g_idx` (act-order; only a hand-made unit test, no library reference), GPTQ-Marlin / Marlin repacked symmetric 4- and 8-bit weights (also a real 4-bit TinyLlama Marlin repository: coherent text), AQLM, and the `mxfp4`, `nvfp4` and `mxfp8` modes of MLX. HQQ, torchao, Quark, EETQ, QuIP#, SpQR, VPTQ, HIGGS and fp_quant checkpoints are still refused; the error now names the reason and the way out. New scripts: `scripts/make_ct_int_fixtures.py`, `make_mlx_fp_fixtures.py`, `make_marlin_fixtures.py`, `make_aqlm_fixtures.py`, `st_peek.py` (safetensors header over HTTP).

### Added (NPU, 4-bit weights)
- **AMD XDNA 2 NPU: weights stay 4-bit and the native block-floating-point MAC does the multiply.** Q4_0, Q4_1 and Q4_K weights are kept as packed 4-bit tiles (0.625 byte per weight; 1.4 GiB instead of 5.4 GiB of bf16 for a 3B model), expanded inside the compute tiles of the NPU (`rust/engine/xdna/kernel_src/fllm_dq.cc`, derived from the `q4nx` kernel of mlir-aie) to block floating point and multiplied on the bfp16 MAC of AIE2P with f32 sums (`fllm_mm_bfp.cc`): 5.7 TFLOPS for an 8192 x 3072 Q4_K projection at 512 rows against 1.2 on the processor and 2.0 with the bf16 MAC of the first version. Llama-3.2-3B Q4_K_M on a Ryzen AI 5 PRO 435 laptop (Linux, nothing else running): prompt of 400 tokens 310-314 tok/s (processor 155-168; the first version: 187-190), of 1180 tokens 222-227 (processor 117-131; the first version: 167-169), of 160 tokens 261-265; the greedy text of a 714-token prompt equals the processor's; the self test passes (error about 0.75 % of the largest result per projection). `FLLM_XDNA_PRECISION=exact` keeps bf16 products. At 1180 tokens the attention on the processor (1.85 of 5.1 s) is the largest part and the remaining gap to FastFlowLM's 306 tok/s; decode on the NPU was measured (1.2 ms for a 64-row call against 0.9 ms on the processor for one row; 4 or more rows are 2 times faster per projection but whole-model decode did not gain) and stays on the processor. A 64-row program serves small batches. [docs/npu-xdna.md](docs/npu-xdna.md).

### Added
- **RWKV-6 ("Finch") and RWKV-7 ("Goose") on the CPU.** Time-mix and channel-mix layers with a matrix-valued WKV state per head; the token-shift vectors and WKV matrices live in the recurrent state store next to the Mamba and DeltaNet states (concurrent sequences, position check, state snapshots), so these models are marked stateful (no prefix sharing, no speculation). `fllm-rs convert` reads the flash-linear-attention RWKV-7 layout and the Hugging Face RWKV-6 layout and writes the llama.cpp tensor names; the loader also reads llama.cpp RWKV GGUFs (fused mixing vectors, pre-scaled RWKV-6 weights). New `rwkv` tokenizer model (greedy longest match over byte strings), built by the converter from `rwkv_vocab_v20230424.txt`. On an accelerator request the model reports `an RWKV time-mix / channel-mix layer (host only)` and runs on the CPU. Verified: tiny random checkpoints against the new `scripts/rwkv_reference.py` (RWKV-7 4.7e-7, RWKV-6 1.1e-6 relative logit difference, `scripts/verify_generation.py` identical greedy text with four concurrent requests) and the real RWKV-7 0.1B and RWKV-6 1.6B checkpoints (1.9e-6 / 1.8e-6 after conversion, 2.4e-4 / 4.2e-4 for the llama.cpp F16 GGUFs, arg-max equal). Not done: device kernels for the WKV recurrences, raw BlinkDL `.pth` checkpoints, quantised RWKV GGUFs were not run. The quantizer keeps the mixing vectors and adapters of RWKV in full precision.

- **One model over several devices of any backend mix.** `--device cuda:0,vulkan:1,cpu` (two or more devices, each once) splits the layers over them in proportion to their free memory and speed (`--tensor-split 3,1` overrides the speed estimates): every stage holds the weights and the KV cache of its own layers, the output head sits on the last stage, a decode step flows through the stages and the activations cross between devices through host memory (no peer path needed). `--tensor-parallel N|auto` (alias of `--tensor-parallel-size`) cuts every layer over N devices of one backend; the row-parallel results are added with the group's all-reduce (NCCL for CUDA when libnccl is found, else host memory) and the output head is cut by vocabulary rows; mixture-of-experts layers run through the sharded or expert-parallel experts (the host path for the all-to-all combine). The planner (`parallel/split.rs`, `backend/memory.rs::plan_pipeline`) fits every stage into its memory next to a shared KV pool, lowers the context when one full sequence does not fit, and refuses with the numbers per device. The log, `fllm-rs devices --split MODEL --device A,B,C` (dry run) and the Studio hardware card (`split` / `devices[].split` in `/api/studio/hardware`: stage, layers, share per device) show the split. The server used to parse `--tensor-parallel-size` / `--pipeline-parallel-size` and then ignore them (the runtime never called the parallel loader); it calls it now, on the CPU and on devices. Proven: pipeline and tensor-parallel equivalence tests that run the staged **device** forward pass with the CPU backend standing in for a GPU (logits of 16 steps and greedy tokens against the single-device run, Q4_K, Q8_0, F16, F32, Q4Z, NVFP4, QK-norm, biases, Gemma-2 features, uneven ranges, device stages next to host stages) and planner unit tests over many device-count / size combinations. Run on one laptop (RTX 2000 Ada and Intel RPL-S iGPU through Vulkan, plus the CPU; Llama-3.2-3B Q4_K_M): layer splits over the pair, NVIDIA plus CPU and a tensor-parallel group of the two Vulkan devices give coherent text at 20 to 54 tok/s against 98 to 140 on the NVIDIA GPU alone (the split is as fast as its slowest stage; it pays when the model does not fit one device or several requests keep the stages busy). **Not measured / never run:** speed-ups on several equal GPUs, NCCL and peer-to-peer all-reduce between CUDA cards from the device pass, HIP / Metal in a split, device-side expert kernels in a tensor-parallel group, Windows at run time (the cross-build compiles). Limits (Gemma 3n/4 per-layer inputs, MTP, latent MLA, draft-model speculation, CUDA graphs, KV block copies are off in a split) in [docs/multi-gpu.md](docs/multi-gpu.md).

- **The AMD XDNA 2 NPU with fLLM's own kernels** (feature `npu-xdna-native`, in the default set; no vendor inference library, FastFlowLM stays as it was). A bf16 GEMM program (f32 accumulation, 8 x 4 compute tiles) built from the open mlir-aie / Peano toolchain is embedded in the binary and run through XRT by way of a 12-function C++ shim that is opened at run time (`fllm-rs amd-npu build-shim`; no shim, XRT or device: the backend reports unavailable and nothing else changes). The large prompt projections (64 or more rows) of any GGUF model run on the NPU, with the quantized weights expanded to bf16 when a tile is packed (resident while a memory budget lasts, else packed again per call; Q4_0, Q8_0, Q4_K, Q6_K, F16, BF16, F32 have fast decoders, every other format goes through the generic dequantizer); decode stays on the processor. Routes: `FLLM_NPU_HOST=1` (the fast host decoder offloads; no second copy of the weights) and `--device npu:0` (hybrid with the reference CPU backend, like the Intel route). Checked on one Ryzen AI 5 PRO 435 laptop under Linux (XRT 2.21.75, kernel 7.0): the `linear`/`host`/`embedding` self test passes (183 + 576 checks, 388 projections computed on the NPU, error below the 4e-3 tolerance); a 714-token prompt through Llama-3.2-3B Q4_K_M gives the processor's greedy text; a 1180-token prompt is processed at 169-180 tok/s against 131-136 on the 6-thread processor and 211-216 on the iGPU (Vulkan); a Q4_K projection runs at 2.2 TFLOPS on the NPU against 1.0 on the processor at 512 rows, and 3.4 times slower than the processor for a single row (decode). FastFlowLM, with AMD's kernels, is faster (306 tok/s prompt). The Studio's AMD NPU card and `fllm-rs amd-npu status` say whether the native route is usable; `fllm-rs amd-npu native-bench`, `scripts/npu_prompt_bench.py`, `scripts/npu_text_check.py` measure it. Not tested: Windows (the notes are written down; the cross-build compiles), other XDNA chips, macOS. [docs/npu-xdna.md](docs/npu-xdna.md).
- **Ling-3.0 (`bailing_hybrid`, GGUF architecture `kimi-linear`).** The Kimi-Linear layer mix with the Ling variations: direct (not low-rank) forget and output gate projections (`ssm_f`, `ssm_g`), the bounded forget gate (`kda_safe_gate`, `kda_lower_bound`), rotary latent attention (interleaved pairs) with a head-wise sigmoid output gate on the attention layers (`attn_gate`). The converter reads the Hub layout (`attention.*`, `dense`, `word_embeddings`, separate `q_conv1d` / `k_conv1d` / `v_conv1d`, per-expert `mlp.experts.N.*`, `mlp.gate.expert_bias`) and the transformers 5 layout (one `conv1d`). Checked against transformers 5.22.1 with a tiny random fixture (3 delta layers, 1 latent attention layer, dense first layer): relative logit difference 3.9e-5 .. 4.7e-5 on 12, 20, 33 and 40 positions, also with cached decoding and in greedy server completions (4 concurrent requests identical); the Kimi-Linear fixture is unchanged (8.2e-5). The latent attention gate runs on the host layer path (accelerators run those layers there); no real Ling checkpoint was run.
- **Hy4 (`hy_v4`, GGUF architecture `hy4`), CPU.** Latent attention with the lightning indexer (layers marked `shared` reuse the selection; the indexer rotates the last `qk_rope_head_dim` values of its heads with half-split pairs and norms its keys with the model epsilon), sinks, a per-element sigmoid gate on the attention output, independent hyper-connections (`hc_mult` streams, no mixing matrix, `post = magnitude * sigmoid + eps`), sigmoid-routed MoE whose routed experts use a clamped SwiGLU (the shared expert is not clamped). Checked against transformers 5.22.1 with a tiny random fixture (6 layers, indexer keeps 4 keys, 3 streams): relative logit difference 1.4e-4 .. 1.7e-4 on 12, 20, 33 and 40 positions, also with cached decoding and in greedy server completions (4 concurrent requests identical); with the indexer disabled (`FLLM_DSA=dense`) the same fixture is off by 0.55. Accelerators say so and run on the CPU. Hub names (`hc_attn_layer.hc_fn`, `learnable_sink_param`, `linear_gate`) are renamed as in the transformers conversion mapping; no real Hy4 checkpoint was run.
- **DeepSeek-V4 (`deepseek_v4`, GGUF architecture `deepseek4`), CPU.** Manifold-constrained hyper-connections (several residual streams, Sinkhorn-projected mixing), shared-KV multi-query attention with a sliding window, compressed sparse (indexer, overlapping windows) and heavily compressed layers, rotary embeddings undone on the attention output, sinks, grouped low-rank output projection, hash-routed and top-k MoE layers (`sqrtsoftplus` scores, clamped SwiGLU, token-id-to-expert table). The converter reads the transformers layout and the Hub layout (`layers.N.attn.wq_a`, `hc_attn_fn`, per-expert `w1`/`w2`/`w3`; renames follow the transformers conversion mapping), writes the YaRN-corrected rotary tables as tensors and the integer routing table as f32. Per-sequence state (window ring, pooling buffers, overlap, compressed entries, indexer entries) lives in the recurrent-state store, so prefix sharing and rollback are off for this model. Checked against transformers 5.22.1 with a tiny random fixture (4 layers: window only, compressed sparse x2, heavily compressed; 3 streams; YaRN on the compressing layers; 6-token window, indexer keeps 3): relative logit difference 5e-7 .. 1e-6 on 12, 20, 33 and 40 positions, also with cached decoding and in greedy server completions (4 concurrent requests identical to transformers). Not done: the multi-token-prediction head (the transformers class has none), FP8 / FP4 Hub checkpoints (convert from a bf16 export), accelerators (`--device` says so and runs on the CPU), a real checkpoint.
- **DeepSeek sparse attention (lightning indexer) of DeepSeek-V3.2 and GLM-5, exact.** The converter keeps the `self_attn.indexer.*` tensors (`blk.N.indexer.attn_q_b`, `attn_k`, `k_norm`, `proj`, metadata `attention.indexer.head_count` / `key_length` / `top_k`, plus `rope_neox`); GGUF files with the llama.cpp architecture names `deepseek32` and `glm-dsa` load as `deepseek2`. The CPU path scores every earlier token per layer (`sum_h w_h * relu(q_h . k)`), keeps the `index_topk` best and attends to those only; GLM-5 layers marked `shared` reuse the selection of the layer before. The indexer keys sit beside the KV pools by cache slot, so block copies (n > 1 choices) and swaps carry them. Checked against transformers 5.22.1 with tiny random fixtures whose indexer keeps 4 of 12 / 33 / 36 tokens (`deepseek_v32_sparse` 1.7e-4, `glm_moe_dsa_sparse` 3.5e-4 relative on every position; with the old dense attention the same fixtures are off by 0.57 / 0.64) and with cached decoding (`FLLM_VERIFY_SPLIT`, greedy server completions of 4 concurrent requests identical to transformers). On accelerators the layers keep their dense device kernels (exact up to `top_k` tokens) and say so once; `FLLM_DSA=exact` runs them on the host, `FLLM_DSA=dense` forces dense attention everywhere. There is no device kernel for the indexer yet.

- **The Intel NPU (OpenVINO) became usable.** Measured on a Core Ultra 5 235U (NPU 3720, Windows 11): the earlier "195 s start" was the self test's reference CPU backend, not compilation. Compiling depends on the weight form: INT4 in groups of 32 took 40 to 90 s per large projection (338 s once), groups of 128 5 to 12 s, per-channel INT8 0.7 to 1.2 s, and the per-channel forms also run fastest. The offload now stores every integer format as **INT8 per output channel** (`FLLM_NPU_WEIGHTS=int4|exact` keep the old forms), uses chunks of 256 rows, and `--device npu` runs the fast host decoder with the prompt projections on the NPU (the old hybrid backend only with `--npu-mode all` / `FLLM_NPU_HYBRID=1`). Compiled programs are cached on disk (second start: about 40 ms per program instead of about a second); on a cold cache they are compiled by a background thread while the processor serves the prompts, so the server and the first prompt do not wait. On an RTX 2000 Ada (8 GB, Vulkan) the model now loads with all 16 layers on the device and decodes at 81-97 tok/s (it ran out of memory before).
- **HIP/ROCm: a long prompt takes a 128-token tile.** The matrix-core GEMM decodes every weight once per token tile; with 128 instead of 64 tokens per tile that cost is shared by twice the products. Llama-3.2-3B Q4_K_M on a Radeon 840M (gfx1153): prompt 160 -> 188 tok/s (501-token prompts); `FLLM_HIP_NARROW_TILE=1` switches back. GPU self-test on that device: 0 failures.
- **HIP/ROCm: no rocWMMA needed any more.** The prompt GEMM of `hip_gemm.cu` (MFMA / WMMA) does not use it, the rocWMMA kernel of `tc_gemm.cu` is built only with `-DFLLM_HIP_ROCWMMA` (rocWMMA does not know `gfx1150`..`gfx1153` and Ubuntu packages it incompletely). An AMD APU is classified as an integrated GPU and its memory is scaled to the three quarters the ROCm runtime hands out (a Radeon 840M with 7.7 GB failed at about 6 GB); a weight whose pages are page-locked in several pieces is copied piece by piece (the HSA runtime refuses a copy across pieces: "invalid argument" with MoE experts).
- **GPU self-test and host fallback:** the CUDA/HIP host fallback of `moe_expert_gemm` reads Q8_0, Q4_0/Q4_1/Q5_0/Q5_1, IQ4_NL and Q6_K weights back from the device layout (it produced NaN); the int8 W8A8 check is skipped on devices without that GEMM.

### Fixed
- `/v1/audio/transcriptions` and `/v1/audio/translations` returned a made-up placeholder (`[audio transcript: N frames ...]`) as if it were a transcript. They now answer **501** (`speech-to-text is not implemented`) for a readable file and 400 for a damaged one. The Whisper encoder and the log-mel frontend are unchanged; the text decoder is still missing.
- README and roadmap listed Qwen-VL, Gemma 4 and multi-GPU as missing; the code has Qwen2/2.5/3-VL, Gemma 4 text models and CPU-proven tensor/pipeline/expert parallelism. The texts now say what exists and what is only proven on the CPU.
- **Vulkan: "Vulkan device lost" on prompts of a few hundred tokens on small GPUs.** A whole model step was one GPU submission, and a driver ends a job that runs too long (Windows TDR: 2 s; Linux amdgpu: the compute ring timeout, followed by a reset). On a Radeon 840M a prompt of about 400 tokens ran into it. A submission now holds at most 1.5e11 multiply-adds of the projections (`FLLM_VK_SUBMIT_MACS` changes it); prompts of 1124 tokens run with no timeout (219 to 243 tok/s), and the cooperative-matrix shaders are fine (they ran too long at a stretch, nothing more).
- **Memory plan, four faults found on a Radeon 840M and an 8 GB RTX 2000 Ada:** (1) the context that keeps every layer on the device was counted against the free memory while the plan checks the utilization budget, so the plan with that context sent feed-forward weights to the host; (2) the Marlin copy of Q4_K weights, which only the CUDA backend uses, was counted for every backend (1.5 GB for a 3B model); (3) when the whole model does not fit, the context is capped at 8192 tokens so that more feed-forward layers stay on the device; (4) with an automatic context the plan kept the full context (32768 tokens) and moved the feed-forward weights of all 32 layers of Llama-3.1-8B to the host, because the full context fit next to the attention weights. With an automatic context every layer now stays on the device when at least 4096 tokens fit next to it (the log says how to get the long window back: `--ctx 32768`). Llama-3.1-8B Q4_K_M on an 8 GB card with the native Vulkan backend: 10 to 14 tok/s before, 32 to 34 tok/s after (context 10320), prompt 16 to 75 before, 364 to 657 tok/s after.
- **CUDA on Turing (T4, RTX 20 series): Q4_K_M models wrote nonsense.** The fused gate/up activation of the quantized prompt GEMM is used from Ampere (sm_80) only; with it switched off (`FLLM_CUDA_NO_GLU_FUSE=1`) the T4 gave the right text. Found with the new switch-by-switch test (`scripts/colab/gpu_test.py` (Colab) and `scripts/gpu_test.py` (any Linux machine)); the fix has not run on a T4 yet.
- **CUDA int8 W8A8 GEMM** (`FLLM_INT8_GEMM=1`) computed one quarter of the output rows (the launch divided the rows by 128 / 256, a block covers 32 / 64) and left the rest unwritten. **FlashInfer tensor-core decode** (`FLLM_ATTN_DECODE=flashinfer`) called FlashInfer's CUDA-core decode kernel without a decode plan (illegal memory access); it uses the planned prefill kernel as documented. `FLLM_MARLIN_PREFILL_CFG=fllm` is ignored below Ampere (it gave other results than the split on a T4). Not run on a GPU after the fixes.
- Self test: the FP8 W8A8 direct cases skip below sm_89, the merged-QKV rope positions stay inside the 64-position table, and the bf16 attention / chain and the FlashInfer prompt checks count the rounding of the narrow output.
- Block-wise FP8 checkpoints with 128 x 128 tiles could be converted but not loaded: the GGUF reader did not count the scales into the tensor size and the loader guessed the tile layout from byte counts. The new `FP8B` layout (above) describes itself. Block-wise scales were stored as f16 (precision and range lost); they are f32 now. A tile grid of one tile (matrices no larger than a tile) is read as tile scales when the checkpoint declares a block size, and a `weight_scale_inv` whose shape is not the tile grid of its weight is refused instead of being read in the wrong order.
- The grouped MoE GEMM decoded FP8 experts without applying any scale (FP8M row scales sit behind the codes or in the W8A8 / Marlin layouts, block scales were ignored) and the one-to-four-token MoE decode path was declared usable for FP8 experts that it has no kernel for. FP8M experts now take the per-expert path; FP8B experts have scales in the grouped kernel.
- `serve --device cuda --embeddings` (and a vision model with `--mmproj`) failed to start with "unsupported Rust GPU backend cuda": the small helper models (text encoders, vision towers) now run on the CPU when the device is `cuda`, `hip` or another one they cannot use. Found by the A100 run of the Colab check.
- Beam search ignores the repetition penalty a model recommends for sampling instead of refusing every request on such a model (a penalty the request itself asks for is still refused).
- Helm chart: the size and time of the output cache were written as `6.7108864e+07` and ignored by the server (so the default stayed); they are whole numbers now, and `helm lint` passes. `appVersion` follows the release.

- **Block-wise FP8 checkpoints stay 8-bit and run natively** (`weight_scale_inv` of DeepSeek-V3, Qwen3-FP8, GLM-FP8, MiniMax and others). The fLLM-specific GGUF type `FP8B` holds the E4M3 codes exactly as in the checkpoint, one **f32** scale per tile and a 16-byte trailer with the geometry (columns, rows, matrices), so a tensor describes itself: 1.0002 bytes per weight for 128 x 128 tiles. The tile shape is part of the type id (`0x8000_0021` is 128 x 128, `0x8000_0100 | log2(rows) << 4 | log2(columns)` any other power-of-two tile); scales in f32, bf16, f16 or UE8M0 (`F8_E8M0`, DeepSeek-V3.1 and later) are read; stacked experts carry the scales of every expert. - Thinking only where the model can think: the status route and `/v1/models` report `capabilities.thinking` (`control` none / toggle / effort / always, the template variable, the levels and the default), read from the chat template, the reasoning parser and the architecture. The Studio shows its Thinking chip only for models that can think, with the levels the model has (Off / Low / Medium / High for models with a switch, Low / Medium / High for effort models such as gpt-oss), remembered per chat.
- Thinking budget: `thinking_budget` (tokens) in chat requests, and `reasoning_effort` low / medium on models with a thinking switch (512 / 2048 tokens), end the reasoning block after that many tokens: the server appends the closing tag and the model writes its answer, in streams and normal replies alike ([docs/server-api.md](docs/server-api.md#thinking)).
- Speculative decoding is chosen in the load dialog (Models, Advanced: off, prompt lookup, draft model, multi-token prediction) and remembered per model; impossible choices (models with recurrent layers, a model without MTP heads, MTP on a backend without it, a draft model that is larger or has another vocabulary) are refused with a message. The switch in the sampling panel is gone: it only asked the server to skip speculation per request, and the server already does what the start option says.
- Studio chat that decides for itself: *Use the web* became *Allow web access* and offers the model `web_search` and `web_fetch` as tools instead of searching every question (compact "Searched" / "Read" cards, sources under the answer, at most 5 rounds, Stop works, results sized to the context, `tool_call_grammar`). A default system prompt in a compact and a full size with adjustments per model family (date and time, language, honesty, tool rules; shown and overridable or extendable in Settings > Personalization and per assistant). A `memory` tool the model manages (add, update, remove, list; "Saved to memory" cards with Undo; secrets refused; per-chat and global switch) with a server-side copy (`GET`/`PUT /api/studio/memory`, `memory.json`, this machine only), and a `search_chats` tool for earlier chats (asked once per chat). Chat titles use a short prompt that works with thinking models.
- Studio, Code: a larger step towards a full coding agent ([docs/user/studio.md](docs/user/studio.md)). New tools: `patch` (unified diff over several files, all or nothing), `diagnostics` (syntax / build check with `cargo check`, `tsc`, `go vet`, `py_compile`, `node --check`; optional "check my edits automatically"), `memory`, `todo_read`, and `task` with sub-agent types `explore` (read only) and `general`. `edit_file` tolerates indentation differences, keeps CRLF files CRLF and, when it fails, names the closest text with line numbers; `read_file` suggests similar names for a missing file and refuses binary files and images clearly; `list_dir` shows a tree (`depth`); `grep` has `literal` and `word`; `glob`, `grep` and the tree respect `.gitignore`.
- Studio, Code: separate system prompts for the build, plan and sub-agents, a compact form for small models and contexts, a note with an example call per model family (Qwen, Llama, Mistral, Gemma, gpt-oss), an environment block (folder, system, shell, git state, date), project instructions from `AGENTS.md` / `FLLM.md` / `CLAUDE.md` of the folder and its parents, and a persistent memory per folder and per user that the model maintains itself (`.fllm/memory.md`, `agent-memory.md`; panel in the side bar, `/remember`, `/memory`).
- Studio, Code: sessions can be forked from any message, reverted to a message (conversation and file changes, with an undo of the revert), renamed, deleted, searched and exported as Markdown; the model titles them. Build / plan agent switch (Alt+B) and a model switch in the header, a message queue while the agent works, `!command` shell escape whose output the model sees, fuzzy `@` file search over the folder, a permission table (allow / ask / deny per kind of action and agent) next to the pattern rules, and new routes `/api/studio/agent/{cancel,files,memory,instructions}`; `POST /api/studio/agent/undo` takes `{"redo": n}`.
- Vulkan: a new tiled matrix-matrix kernel for prompt processing with quantized weights (`mmq_<format>_i`, used from 32 rows up on GPUs with the int8 dot product), and the shaders now emit the dot-product instruction themselves when the shader compiler is too old to do it (the Windows release build was affected). Compiled and unit tested, not yet measured on a GPU; `FLLM_VK_MM=0` switches the kernel off, `FLLM_VK_MM_BM` / `FLLM_VK_MM_BN` tune the tile ([docs/changes/vulkan-prefill.md](docs/changes/vulkan-prefill.md)).
- NPU: a load option "What the NPU computes" (`--npu-mode all`): besides the long prompt blocks the NPU then also computes the single rows of the answer, the way later and stronger NPUs will be used. Measured on an Intel Core Ultra NPU with Qwen3.5-2B Q4_K_M: the answer runs at about 5 tokens/s this way (after a one-time compile of a few minutes that OpenVINO keeps in its cache), about as fast as the processor and well below the graphics chip.
- `--threads auto` (the new default): the CPU thread count follows the processor's topology (one thread per physical core; on hybrid processors all fast cores plus three quarters of the efficiency cores, never the low-power ones) and is confirmed by a measurement of about a second on the real weights at start-up, remembered per CPU, weight type and matrix shape (`FLLM_NO_AUTOTUNE=1` skips it). The old default of one thread per logical processor was less than half as fast for answers as 8 threads on a 14-thread hybrid laptop. Prompts keep all logical processors when all cores are alike; on Windows hybrid processors the process leaves power throttling and stays on the chosen cores (`FLLM_NO_PIN=1` disables that). `fllm-rs devices` and `/api/studio/hardware` report the topology and the thread count ([docs/cpu-kernels.md](docs/cpu-kernels.md#thread-count)).

### Fixed
- Studio, Code: a command that hit its time limit left its child processes running and the call waited on their output pipes; the whole process tree is ended now, also when Stop is pressed. Command output keeps stdout and stderr in order and keeps its end when it is cut. Stopping the agent now leaves valid history (unanswered tool calls get an "interrupted" result, two user messages in a row are separated) and runs one after another instead of overlapping. A failed edit no longer leaves an entry in the change log. On Windows, an absolute path with a different drive-letter case is accepted, glob patterns ignore case and multi-line commands are joined for `cmd`.
