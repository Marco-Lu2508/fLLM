## [0.1.12] - 2026-10-30

### Added
- **Vulkan: the faster prompt matrix shader is chosen per device.** The first prompt-sized projection times a 4096 x 4096 Q4_K product with the cooperative-matrix shaders and with the int8 dot-product shaders (a few milliseconds) and keeps the faster one: cooperative matrices on an RTX 2000 Ada (1.2 against 3.4 ms), the int8 dot product on a Radeon 840M (10.4 against 14.0 ms; prompt 176 -> 214 tok/s). `FLLM_VULKAN_NO_TUNE=1` keeps the old order. On AMD two matrix-vector rows per work group instead of one (+12 % decode on the 840M).
- **The ROCm/HIP backend ran on an AMD GPU for the first time** (Radeon 840M, `gfx1153`, Ubuntu 26.04 with ROCm 7.1 from the distribution): `selftest-gpu --device hip:0` 821 checks ok, 13 failed (int8 W8A8 against an exact reference, one MoE case), 470 skipped; the text of dense models equals the CPU's. Kernels that exist for NVIDIA only (device MoE routing, GPU sampling, latent MLA, encoder attention) are now reported as unsupported, which callers answer with their host path and the self test skips, instead of as a failed driver call. MoE models and host-streamed layers still fail on this APU: a 1.1 MB host-to-device copy (one expert matrix of OLMoE, from a pinned host buffer into a device buffer) is refused with "invalid argument"; the error message now names the pointers.
- **The NPU of an AMD Ryzen AI processor, through FastFlowLM.** fLLM finds an installed `flm`, shows what `flm validate` says about the NPU stack (driver, firmware, the memlock limit), lists the models, downloads them, starts `flm serve` for one model as a process it manages and lists that model as the provider "AMD NPU (FastFlowLM)" (removed again when it stops): Settings > Hardware has a card for it, `fllm-rs amd-npu status|list|pull|serve [--register]` the same on the command line, the routes are `/api/studio/npu/amd` (this machine only). Checked on a Ryzen AI 5 PRO 435 laptop (Ubuntu 26.04, FastFlowLM 1.0.11): Llama-3.2-3B ran at 31 tok/s decode on the NPU through the Studio; the Windows build runs and reports "no NPU" on a PC without one, an AMD NPU on Windows is untested. FastFlowLM is installed by the user; its NPU binaries are AMD's and free to use. [docs/user/amd-npu.md](docs/user/amd-npu.md).
- `scripts/bench_compare.py`: the same client for fLLM, llama.cpp, Ollama, vLLM, SGLang and FastFlowLM; `scripts/gpu_test.py` and `scripts/colab/gpu_test.py`: self test per group, real models against the CPU and a switch-by-switch run. Results of a night on an RTX 2000 Ada and a Radeon 840M laptop (also against the AMD NPU) are in [docs/benchmarks.md](docs/benchmarks.md).
- **`fllm-rs agent -p "task"`: the coding agent without a browser.** It runs the Studio's tools over HTTP against a server on the same machine; reading is always allowed, edits, commands, network and memory only with `--allow-edit`, `--allow-command`, `--allow-network`, `--allow-memory` (or `--yes`). Refused calls are not run and the model is told why. Sessions (`--session`), a JSON result (`--json`), trajectory export (`--trajectory`), exit codes (0 / 1 / 3), a repeat guard and a context-size check. [docs/user/agent-cli.md](docs/user/agent-cli.md).
- **`fllm-rs gateway telegram` and `fllm-rs gateway matrix`: talk to the agent from a messenger.** Allowlist of chats or room ids (required), one session per chat, `/new`, the same permission flags; the tokens come from `FLLM_TELEGRAM_TOKEN` / `FLLM_MATRIX_TOKEN` only. Matrix answers with `m.notice`, ignores its own messages and accepts invites to listed rooms only; encrypted rooms are not supported. The stream position is saved (`gateway-<kind>.cursor`), so nothing is answered twice.
- **Agent: project instructions and memory, persona, profiles, `--ask`.** The run reads `AGENTS.md` / `FLLM.md` / `CLAUDE.md` and the memories into its system prompt, adds `SOUL.md` as the persona, `--profile NAME` keeps `SOUL.md`, sessions and gateway positions under `profiles/NAME`, and `--ask` asks in the terminal before a call that the flags do not allow.
- **Scheduled tasks can deliver their result** to a webhook, a ntfy topic or a Telegram chat (`deliver` field, *Also send the result to* in the form); the outcome (`sent` / `failed: ...`) is stored with the result.
- `--device opengl` (`gl`): an OpenGL 4.3 / OpenGL ES 3.1 backend through wgpu for graphics cards that have no Vulkan, DirectX 12 or Metal driver. `auto` tries it after DirectX 12 and before the CPU, lists a card only when no other driver serves it and never takes a software renderer. Checked on a software OpenGL (Mesa llvmpipe): the self-test groups linear, activation and norm pass against the CPU and a tiny model writes the CPU's text; not tried on an old graphics card.

### Fixed (AMD, 2026-10-30)
- **Vulkan: the experts of a mixture-of-experts layer exist once on the device.** They were copied into an arena for the expert kernels and the individual copies stayed: OLMoE-1B-7B Q4_K_M did not fit an 8 GB card. The experts are now slices of the arena (`Backend::alias_weights_into_table`). On an RTX 2000 Ada (8 GB, Vulkan) the model now loads with all 16 layers on the device and decodes at 81-97 tok/s (it ran out of memory before).
- **HIP/ROCm: a long prompt takes a 128-token tile.** The matrix-core GEMM decodes every weight once per token tile; with 128 instead of 64 tokens per tile that cost is shared by twice the products. Llama-3.2-3B Q4_K_M on a Radeon 840M (gfx1153): prompt 160 -> 188 tok/s (501-token prompts); `FLLM_HIP_NARROW_TILE=1` switches back. GPU self-test on that device: 0 failures.
- **HIP/ROCm: no rocWMMA needed any more.** The prompt GEMM of `hip_gemm.cu` (MFMA / WMMA) does not use it, the rocWMMA kernel of `tc_gemm.cu` is built only with `-DFLLM_HIP_ROCWMMA` (rocWMMA does not know `gfx1150`..`gfx1153` and Ubuntu packages it incompletely). An AMD APU is classified as an integrated GPU and its memory is scaled to the three quarters the ROCm runtime hands out (a Radeon 840M with 7.7 GB failed at about 6 GB); a weight whose pages are page-locked in several pieces is copied piece by piece (the HSA runtime refuses a copy across pieces: "invalid argument" with MoE experts).
- **GPU self-test and host fallback:** the CUDA/HIP host fallback of `moe_expert_gemm` reads Q8_0, Q4_0/Q4_1/Q5_0/Q5_1, IQ4_NL and Q6_K weights back from the device layout (it produced NaN); the int8 W8A8 check is skipped on devices without that GEMM.

### Known issues
- On an RTX 2000 Ada laptop GPU (AD107, sm_89) the first part of the `fp8blk` self test (the exact tolerance of 1e-3) fails 20 cases of the FP8 tensor-core path for block-wise FP8 weights: they are 2 to 5 % away from the f32 reference, which is the size of the E4M3 rounding of the activations that path does on purpose; with the tolerance of the fast kernels all 172 cases pass. The cascade attention (`FLLM_CASCADE_ATTN=1`, off by default) returns wrong values, and the f16 activation pipeline (`FLLM_ACT_DTYPE=f16`, off by default) fails its merged QKV and gate/up checks. None of these is on the path of a GGUF model with default settings.
- The Vulkan backend with the wgpu route (`--device wgpu-vulkan`, and the Colab test build, which has no native Vulkan) is several times slower than the native Vulkan backend of the release packages (8 against 28 tok/s on a Radeon 840M).

### Security
- `zip` 9.0.4 -> 9.0.5 (the PyTorch and archive reader of the converter; CVE-2026-115905, found by the Trivy scan).

### Fixed
- `/v1/audio/transcriptions` and `/v1/audio/translations` returned a made-up placeholder (`[audio transcript: N frames ...]`) as if it were a transcript. They now answer **501** (`speech-to-text is not implemented`) for a readable file and 400 for a damaged one. The Whisper encoder and the log-mel frontend are unchanged; the text decoder is still missing.
- README and roadmap listed Qwen-VL, Gemma 4 and multi-GPU as missing; the code has Qwen2/2.5/3-VL, Gemma 4 text models and CPU-proven tensor/pipeline/expert parallelism. The texts now say what exists and what is only proven on the CPU.
- **Vulkan: "Vulkan device lost" on prompts of a few hundred tokens on small GPUs.** A whole model step was one GPU submission, and a driver ends a job that runs too long (Windows TDR: 2 s; Linux amdgpu: the compute ring timeout, followed by a reset). On a Radeon 840M a prompt of about 400 tokens ran into it. A submission now holds at most 1.5e11 multiply-adds of the projections (`FLLM_VK_SUBMIT_MACS` changes it); prompts of 1124 tokens run with no timeout (219 to 243 tok/s), and the cooperative-matrix shaders are fine (they ran too long at a stretch, nothing more).
- **Memory plan, four faults found on a Radeon 840M and an 8 GB RTX 2000 Ada:** (1) the context that keeps every layer on the device was counted against the free memory while the plan checks the utilization budget, so the plan with that context sent feed-forward weights to the host; (2) the Marlin copy of Q4_K weights, which only the CUDA backend uses, was counted for every backend (1.5 GB for a 3B model); (3) when the whole model does not fit, the context is capped at 8192 tokens so that more feed-forward layers stay on the device; (4) with an automatic context the plan kept the full context (32768 tokens) and moved the feed-forward weights of all 32 layers of Llama-3.1-8B to the host, because the full context fit next to the attention weights. With an automatic context every layer now stays on the device when at least 4096 tokens fit next to it (the log says how to get the long window back: `--ctx 32768`). Llama-3.1-8B Q4_K_M on an 8 GB card with the native Vulkan backend: 10 to 14 tok/s before, 32 to 34 tok/s after (context 10320), prompt 16 to 75 before, 364 to 657 tok/s after.
- **CUDA on Turing (T4, RTX 20 series): Q4_K_M models wrote nonsense.** The fused gate/up activation of the quantized prompt GEMM is used from Ampere (sm_80) only; with it switched off (`FLLM_CUDA_NO_GLU_FUSE=1`) the T4 gave the right text. Found with the new switch-by-switch test (`scripts/colab/gpu_test.py` (Colab) and `scripts/gpu_test.py` (any Linux machine)); the fix has not run on a T4 yet.
- **CUDA int8 W8A8 GEMM** (`FLLM_INT8_GEMM=1`) computed one quarter of the output rows (the launch divided the rows by 128 / 256, a block covers 32 / 64) and left the rest unwritten. **FlashInfer tensor-core decode** (`FLLM_ATTN_DECODE=flashinfer`) called FlashInfer's CUDA-core decode kernel without a decode plan (illegal memory access); it uses the planned prefill kernel as documented. `FLLM_MARLIN_PREFILL_CFG=fllm` is ignored below Ampere (it gave other results than the split on a T4). Not run on a GPU after the fixes.
- Self test: the FP8 W8A8 direct cases skip below sm_89, the merged-QKV rope positions stay inside the 64-position table, and the bf16 attention / chain and the FlashInfer prompt checks count the rounding of the narrow output.
- Block-wise FP8 checkpoints with 128 x 128 tiles could be converted but not loaded: the GGUF reader did not count the scales into the tensor size and the loader guessed the tile layout from byte counts. The new `FP8B` layout (above) describes itself. Block-wise scales were stored as f16 (precision and range lost); they are f32 now. A tile grid of one tile (matrices no larger than a tile) is read as tile scales when the checkpoint declares a block size, and a `weight_scale_inv` whose shape is not the tile grid of its weight is refused instead of being read in the wrong order.
- The grouped MoE GEMM decoded FP8 experts without applying any scale (FP8M row scales sit behind the codes or in the W8A8 / Marlin layouts, block scales were ignored) and the one-to-four-token MoE decode path was declared usable for FP8 experts that it has no kernel for. FP8M experts now take the per-expert path; FP8B experts have scales in the grouped kernel.
- `serve --device cuda --embeddings` (and a vision model with `--mmproj`) failed to start with "unsupported Rust GPU backend cuda": the small helper models (text encoders, vision towers) now run on the CPU when the device is `cuda`, `hip` or another one they cannot use. Found by the A100 run of the Colab check.
- Beam search ignores the repetition penalty a model recommends for sampling instead of refusing every request on such a model (a penalty the request itself asks for is still refused).
- Helm chart: the size and time of the output cache were written as `6.7108864e+07` and ignored by the server (so the default stayed); they are whole numbers now, and `helm lint` passes. `appVersion` follows the release.

### Added
- **Native Vulkan shaders for block-wise FP8 (`FP8B`, and `FP8M` converted to one-row tiles), bitsandbytes (`NF4B64/128`, `FP4B64/128`, `INT8R`), MLX affine (`MLXA`, 2 to 8 bits, every group, f16 and bf16 scales), EXL2 and EXL3** on the native Vulkan backend. They used to be expanded to F16 at upload (2 bytes per weight, 4 to 8 times the packed size for the 4-bit formats). The device images are planar like the other Vulkan formats (`weights/layout.rs`, `Geometry`): FP8 keeps one byte per weight plus the tile scale repeated for each row (3 % for 128-wide tiles), NF4 / FP4 / int8 keep the file blocks split into codes and scales, MLX keeps the bit stream (`bits` words per 32 codes, one scale/bias word per group, six shaders cover all 36 types because the group and the scale type are push constants), EXL2 gets a table per block of 32 inputs and its permutation goes through the prepass of the act-order GPTQ weights, EXL3 is uploaded as the blob and run in three passes per 128 tokens (input transform, trellis product with the codebook computed in shared memory, output transform with the scatter through the output map). FP8, NF4 and FP4 decode to floats and have the f32 shaders (1 to 8 tokens and the 64 x 64 tile); `INT8R`, MLX and EXL2 also have the int8-dot-product, tiled prompt and cooperative-matrix variants. Shapes without a kernel (FP8 rows that are not a multiple of 8 columns or tiles narrower than 8, EXL2 groups that are not a multiple of 32 inputs, EXL3 blobs above one storage binding or not a multiple of 128 in either dimension) still expand to F16 with a notice; `FLLM_VULKAN_NO_EXT_FORMATS=1` switches all of it off. **What ran: every shader on Mesa lavapipe (a CPU implementation of Vulkan) against the CPU kernels in `fllm-rs selftest-gpu --device vulkan` (groups `linear`, `fp8blk`, `mlx`; exact and fast pass, the fast pass also with `FLLM_VULKAN_FORCE_IDOT=1`; 0 failures), and the layouts, decoders (as Rust transcriptions of the GLSL), planner and the upload in unit tests. What did not run: any physical GPU (the AMD Radeon 780M, Intel iGPUs and NVIDIA cards are the next round), the cooperative-matrix variants (lavapipe has none), any speed measurement.** The self test group `fp8blk` now runs on every backend that lists `FP8B` (the tensor-core checks stay CUDA-only), the exact pass checks EXL2 and every EXL3 width and codebook, and a device that falls back to F16 for a shape is judged against the F16 tolerance. Details: [docs/gpu-backends.md](docs/gpu-backends.md#native-vulkan-block-wise-fp8-bitsandbytes-mlx-affine-and-exl2--exl3).
- **Metal kernels for block-wise FP8 (`FP8B`, every power-of-two tile), bitsandbytes (`NF4B64/128`, `FP4B64/128`, `INT8R`) and EXL2 weights** on the native Metal backend (Apple silicon). They used to be expanded to F16 at upload (2 bytes per weight). The device image of `FP8B` and bitsandbytes is the GGUF tensor itself (no copy for memory-mapped models); EXL2 gets its own image with a per-chunk table and the act-order prepass for the stored-order inputs. Same kernel family as the other quantized formats (matrix-vector for 1 to 8 tokens, `simdgroup_matrix` tiles above), arithmetic as the CPU kernels; the shared bodies call a new decoder selector so that formats whose chunk depends on the weight row (FP8B tile scales, EXL2) fit. Escape hatches: `FLLM_METAL_NO_FP8B=1`, `FLLM_METAL_NO_BNB=1`, `FLLM_METAL_NO_EXL=1` (like `FLLM_METAL_NO_MLX=1`; the weights are then expanded to F16 as before). EXL3, and EXL2 blobs with a group that is not a multiple of 8 inputs, stay expanded. **The new MSL has only been linted, compiled as C++ and run on the CPU (decoders bit for bit against the Rust reference, the matrix-vector body on emulated threadgroups) and its Apple-only Rust code type-checked and clippy-checked from Linux: no Metal compiler and no Apple GPU has seen it yet.** The Apple-silicon CI job now runs `metal_quant_kernels` (every format against the CPU dequantization) as a separate step; its first run is the test.
- **Block-wise FP8 checkpoints stay 8-bit and run natively** (`weight_scale_inv` of DeepSeek-V3, Qwen3-FP8, GLM-FP8, MiniMax and others). The fLLM-specific GGUF type `FP8B` holds the E4M3 codes exactly as in the checkpoint, one **f32** scale per tile and a 16-byte trailer with the geometry (columns, rows, matrices), so a tensor describes itself: 1.0002 bytes per weight for 128 x 128 tiles. The tile shape is part of the type id (`0x8000_0021` is 128 x 128, `0x8000_0100 | log2(rows) << 4 | log2(columns)` any other power-of-two tile); scales in f32, bf16, f16 or UE8M0 (`F8_E8M0`, DeepSeek-V3.1 and later) are read; stacked experts carry the scales of every expert. The CPU multiplies the codes directly (`cpu_fp8.rs`: integer E4M3 expansion with the tile scale, AVX2+FMA chosen at run time, NEON and portable code otherwise, results independent of the thread count); the per-tensor / per-channel `FP8M` weights of ModelOpt and compressed-tensors checkpoints use the same loops now (they ran a scalar loop that decoded every element on its own). CUDA (`cuda/fp8_block.cu`): the weight stays 8-bit on every NVIDIA GPU; decode batches of 1 to 16 tokens run an FP32 GEMV that expands the codes in registers (any tile shape, exact FP32 arithmetic on the FP32 activations), prompts an FP16 tensor-core GEMM (sm_75 and newer) with the same expansion, and on sm_89 and newer prompts of 128 x 128 weights use the FP8 tensor cores of `fp8_gemm.cu` with activations quantized per token and 128 values (`FLLM_FP8_BLOCK_W8A8=auto|0|1`); the grouped MoE GEMM applies the tile scales of FP8B experts. `FP8M` weights (per-tensor / per-channel scales) that the Marlin FP8 kernel cannot take (below sm_75, widths that are not a multiple of 128) are repacked at upload into one-row tiles and run through the same kernels, 8-bit, instead of being expanded to F32. Vulkan, wgpu, Metal, SYCL and the TPU path expand `FP8B` to F16 at upload with a notice (before: re-quantized to Q5_K, or 4 bytes per weight). **Verified on the CPU:** the kernel against an f64 evaluation of the dequantized weights (odd shapes, eight tile shapes, bias, batches, any thread count, portable and fused loops), scale indexing, the trailer, expert slicing, byte-for-byte loader parity of direct load and convert (tiles 128, 32, 16; dense and MoE), engine logits against the dequantized F32 model (1e-3) and against the F16 expansion of the same checkpoint (4e-3), UE8M0 scales, and host mirrors of the CUDA kernels (decoder formula, GEMV lane/run arithmetic including the warp reduction, tensor-core tile coverage with the constants read from the kernel source, MoE and W8A8 scale addressing). **Verified for CUDA:** `fp8_block.cu`, `moe.cu`, `api.cu`, `fp8_gemm.cu` compile with nvcc 12.8.1 for sm_75/80/89/90/120 (no register spills in the GEMV, 170 registers in the tensor-core kernel), the Rust side builds and passes clippy with `--features cuda`. **Not run on any GPU:** `fllm-rs selftest-gpu --only fp8blk` (new group: all GEMV batch variants, the prompt GEMM, tile shapes, odd shapes, an 8-bit memory check, the FP8 tensor-core path against its emulation and error bound) and the `fp8b` entries of the `linear` and `moe` groups are the checks to run on a Colab A100 / L4 / Blackwell.
- **bitsandbytes NF4, FP4 and LLM.int8() weights stay 4-bit / 8-bit** instead of being expanded to 16-bit when a checkpoint is loaded or converted. Five new fLLM-specific tensor types (`NF4B64`, `NF4B128`, `FP4B64`, `FP4B128`, `INT8R`, ids `0x8000_0040` to `0x8000_0044`, listed by `fllm-rs formats`) hold the packed codes with an `f32` absmax (double quantization is resolved per block, exactly as the library computes it) or the row scale of int8: 4.25 to 4.5 bits per weight for 4-bit, 8.5 for int8, so a bitsandbytes model needs about a third of the memory it needed (the free-memory check no longer counts four times the file size). A row must be a multiple of 64 values and the code book the standard one, otherwise that tensor is expanded to F16 as before; a checkpoint with a tiled int8 `weight_format` is refused instead of being read wrongly. New CPU kernels (`cpu_bnb`: AVX2 + FMA code book lookups with `vpermps`, portable fallback, float activations, up to four tokens per decoded group) and CUDA kernels (a shared-memory byte-pair code book GEMV for 1 to 8 tokens, the FP16 tensor-core GEMM decoding the blocks for prompts). **Verified**: the CPU paths (unit tests against the f64 reference, loader parity direct vs converted, `selftest-cpu`, the decoder's logits against the expanded weights, codebook and double-quantization arithmetic); the CUDA kernels compile with nvcc 12.8 for sm_80/89/90/120 without spills and their arithmetic is mirrored and tested on the host. **Not verified**: no GPU has run the CUDA kernels yet (`fllm-rs selftest-gpu --only linear --quants bnb` is the check), and large real checkpoints were not measured. Vulkan, Metal and the wgpu backend have no kernel for these types and expand them to 16-bit on upload (logged).
- **EXL2 and EXL3 weights stay packed, and run natively.** The converter (and the direct loader) no longer expands EXL matrices to F16: they become the fLLM-specific GGUF types `EXL2` (0x8000_0030) and `EXL3` (0x8000_0031), one self-describing blob per matrix that keeps the EXL2 codes, scale indices, per-group widths (2-8 bits) and input permutation, or the EXL3 trellis tiles with their Hadamard sign vectors, bit for bit (`--dtype f16|f32` still expands; stacked expert tensors are still expanded). The CPU multiplies them without a dense matrix (`cpu_exl.rs`: decode group by group / tile by tile into a small scratch, any OS and architecture), and NVIDIA GPUs from sm_60 read them in place with new CUDA-core kernels (`cuda/exl.cu`). Every other backend (wgpu/Vulkan, Metal, SYCL, TPU, NPU, AMD) expands the blob to F16 once at upload, with a notice, so it stays correct. **Verified:** loader parity (direct load equals the converted file, native and expanded), native blob against the importer's expanded matrix for all EXL2 widths and EXL3 widths 1-8 with the three codebooks, CPU kernels against the dequantized matrix, an end-to-end synthetic EXL2 model against an independent dequantization, bit-level host mirrors of the CUDA arithmetic, and nvcc compilation for sm_75/80/89/90/120. **Awaiting a GPU run:** the CUDA kernels have never executed (`fllm-rs selftest --quants exl2,exl3` checks them against the CPU reference); their speed is unmeasured and they use no tensor cores yet. Details and memory numbers: [docs/exl-formats.md](docs/exl-formats.md).
- **MLX affine checkpoints stay quantized** (mlx-lm / mlx-community exports with 2, 3, 4, 5, 6 or 8 bits and groups of 32, 64, 128 or any other multiple of 32; embeddings and head too). The converter and the direct load used to expand them to F16 (4 bits became 16); they are now fLLM-specific `MLXA<bits>G<group>[B]` tensors (GGUF type `0x8001_0000 | bf16 << 12 | (group / 32) << 4 | bits`) that hold the MLX words, scales and biases as they are: 4.5 bits per weight for 4-bit with group 64. Exactness is checked, not assumed: a tensor stays native only when every scale and bias survives f16 (preferred) or bfloat16 bit for bit; float32 scales without such a form, 7-bit weights and groups that are not a multiple of 32 are expanded to F16 with a warning that says why, nothing is re-quantized. The `mxfp4` / `nvfp4` modes of MLX and stacked experts are refused with a message. CPU kernel (`cpu_mlx.rs`, all widths, AVX2 instance chosen at run time) and the CPU reference of the device tests; CUDA kernels on the packed words (`cuda/mlx_affine.cu`: GEMV, FP32 tile, WMMA tensor cores; device image in `backend/mlx.rs`); Metal kernels for 36 formats on the quantized linear family (`metal/common.metal` `q_fmt_mlx`); every other backend (Vulkan, wgpu, SYCL, NPU, TPU, HIP) gets the weights expanded to F16 by the decoder when it uploads them, with one line on stderr. **Verified:** loader parity direct vs convert (`direct_format_tests`), native blocks bit-identical to the expanding reader on real `mx.quantize` fixtures for every width, unpacking of codes that straddle 32-bit words (3, 5, 6 bit), CPU logits against the dequantized float twin (`import_tests`), a host model of the CUDA GEMV against the CPU reference, the Metal planes and a Rust mirror of the MSL decoder, the MSL decoder text compiled as C++ (107520 values, bit for bit), `nvcc` 12.8 for sm_80/89/90/120 and `cargo check --features cuda`. **Awaiting hardware:** `fllm-rs selftest-gpu --only mlx` on a CUDA GPU (new self test group), the Metal kernels on the Apple-silicon CI runner (`metal_quant_kernels`, `metal/emu/run_emu.sh`), real mlx-community checkpoints on any GPU.
- **Computer use for the coding agent** (off by default; Settings > Runtime > "Let the agent see the screen and use mouse and keyboard", with a warning and a confirmation): ten tools (`computer_screenshot`, `computer_click`, `computer_move`, `computer_drag`, `computer_type`, `computer_key`, `computer_scroll`, `computer_wait`, `computer_cursor`, `computer_displays`) let the agent look at the screen (a PNG scaled to at most 1568 px, coordinates mapped back through display scaling, several displays and zoomed regions) and operate mouse and keyboard in programs that have no API. New permission category `computer`: every action is asked each time (the card shows the last screenshot with a crosshair where it goes), "Always" exists only for screenshots, deny rules win, plan mode and sub-agents never get the tools; a red banner with a STOP button, Esc three times and Ctrl+Alt+Shift+Esc (also watched by the server) cancel the running action and switch it off; actions per minute and per task are limited (settings); a few system-wide key chords (Ctrl+Alt+Del, Alt+F4, lock screen, ...) are refused. Every route is local-machine-only, with or without an API key. No new crates: X11 (Linux), GDI/SendInput (Windows) and CoreGraphics (macOS) are used directly; Wayland is reported as unavailable. Verified end to end on Linux/X11 in Docker (`scripts/computer-use-e2e`); the Windows and macOS layers compile and pass the linter but are not run on real machines yet, and no real vision model has driven it. `FLLM_NO_COMPUTER_USE=1` forbids it on a server. See "Computer use" in `docs/user/studio.md`.
- **An in-app browser for the coding agent** (off until Settings > Browser > "Let the agent use a browser" is switched on). The agent gets `browser_open`, `browser_snapshot` (the page as compact text, a numbered `ref` on every link, button and field, from the accessibility tree), `browser_click`, `browser_type`, `browser_select`, `browser_press`, `browser_scroll`, `browser_back`, `browser_screenshot` (PNG; attached for a model with vision), `browser_tabs` and `browser_close`; every result lists the console errors, uncaught exceptions and failed requests of the page. They drive a real Chrome, Chromium, Edge or Brave over the DevTools Protocol with a small WebSocket client of our own (no new dependency), headless by default, in a profile folder of fLLM's own (`browser-profile`, never the user's browser), with downloads and permission prompts refused. - Jump-forward decoding for grammar-constrained requests (`response_format`, `grammar`, `tool_call_grammar`): where the grammar forces the next characters (the fixed keys and punctuation of a JSON schema, literals in a Lark or GBNF rule), the engine appends them as tokens and the model processes all of them in one forward pass instead of one pass per token. The reply and `usage` are unchanged; with single-character vocabularies the output is token for token identical to decoding without it (tested over many seeds and schemas), with subword vocabularies the text is the same but the token sequence can differ. On the CPU test model the number of forward passes drops by about 5x for compact JSON schemas and literal grammars (for example 486 to 96 over 12 requests); wall-clock speed on real models has not been measured. `--no-jump-forward` or `FLLM_JUMP_FORWARD=off` turns it off; `/metrics` gains `fllm_jump_forward_tokens_total` and `fllm_jump_forward_steps_total`. See [Jump-forward decoding](docs/server-api.md#jump-forward-decoding).
- **Beam search** (`use_beam_search`, with `best_of` as the beam width of 1 to 8, `n` hypotheses returned, `length_penalty`, `early_stopping` `true|false|"never"`) on `/v1/completions` and `/v1/chat/completions`, non-streaming. Beams are ordinary scheduled sequences that share their prefix KV blocks; the score is the sum of token log-probabilities over `length ^ length_penalty`; stop tokens, stop strings, `min_tokens`, `max_tokens`, `logit_bias`, `allowed_token_ids` and `bad_words` are respected. Width 1 equals greedy decoding. Streaming, `logprobs`, repetition/presence/frequency penalties, grammars and images are refused with a clear `400`; a width or token budget the KV pool or the sequence slots cannot hold is refused up front (`400`, or `503` while other searches hold the slots) instead of being queued. See `docs/api-compat.md`.
- **`--multi-step N`** (alias `--num-scheduler-steps`): up to N decode rounds per scheduler round while the batch does not change. Off by default; it applies to the CPU backend only and is ignored (with a message) on accelerators until it is verified there. The output is token for token the one of single steps; speculation, grammar-constrained requests, media and beam search keep single steps. See `docs/speculative-decoding.md` and `docs/dev/step-api.md`.

- `FLLM_STUDIO_DEV=<dir>`: `serve`/`studio` serve the page from that folder on every request instead of the copy embedded at build time, so a CSS or JS change shows up on reload without a rebuild.
- Hybrid models keep a KV cache only for their attention layers: the Gated DeltaNet / Mamba layers of Qwen3.5, Qwen3-Next, Nemotron-H and similar models hold a recurrent state and no keys and values, but the pool reserved room for them too. Qwen3.5 (6 attention layers of 24) now needs a quarter of the KV memory: 1.77 instead of 7.1 GB for the same 9024 blocks, so four times the users or context fit on a card. `FLLM_FULL_KV=1` restores the old layout.
- Gemma 4 on the graphics chip: the device pass now runs the per-layer embeddings, the layer output scale, the value norm, layers whose values are their keys and layers that read an earlier layer's cache (the per-layer weights are uploaded as Q8_0). Measured on an Intel Core Ultra 5 235U (Vulkan) with Gemma 4 E4B Q4_K_M: answers at 12.7 tokens/s (llama.cpp 12.6), prompts at 115 tokens/s (llama.cpp 167); before, the model failed on the device.
- Vulkan prompt speed: the quantized matrix kernel computes 8 x 4 outputs per invocation on a 128 x 64 tile and its loaders read neighbouring bytes of a row (`FLLM_VK_MM_TM`, `FLLM_VK_MM_KS` for tuning), and the Gated DeltaNet recurrence runs over 16 value columns per workgroup with subgroup shuffles instead of one workgroup and a dozen barriers per token and head (`FLLM_VK_DELTA_COLS=0` keeps the old shader). Qwen3.5-2B Q4_K_M, 505-token prompt on the same laptop: 351 tokens/s (0.1.8: 245, llama.cpp: 374).
- Vulkan: a prompt attention kernel with 64 query rows per workgroup on devices that allow 512 invocations (`attn_prefill_*_r64`; `FLLM_VK_ATTN_ROWS=16` keeps the 16-row kernel): +7 % prompt speed at 2000 tokens on Intel Xe-LPG.
- The scheduler now gives running answers their token before new prompt chunks (`--chunked-prefill-policy decode-first` is the default): with several users the first ones get their answer streamed while the later prompts are still read, instead of everyone waiting until the last prompt is done (4 users with 2000-token prompts on Vulkan: first tokens after 9 to 32 s instead of all after 31 s). `prefill-first` restores the old order.
- `scripts/bench-load.ps1`: fLLM, llama.cpp and Ollama under load (prompts of several lengths, several users at once, total and per-user speed, time to the first token).
- `/skill` in the chat and on the Code page: the model writes a skill from the conversation and shows it for approval.
- `FLLM_VK_PROFILE=N` prints the shader table every N command buffers, summed over all recorders of the process.

### Fixed
- A chat on a model with a very small context (under 2048 tokens) failed with "the prompt does not fit": the system prompt plus the tool schemas took more room than the model has. Such models now get a two-line system prompt and no tools, and the page asks for at most a quarter of the window as `max_tokens`, which leaves room for the answer (a 512-token model: 683 tokens before, 249 after the change).
- CPU answers with small models were up to 30 % slower than llama.cpp on server processors: the thread measurement at start-up skipped models whose largest matrix is under 8 MB (it now streams the same projection of several layers, 96 MB per pass, and measures every model), and the Gated DeltaNet recurrence woke rayon's sleeping workers in every layer of every token instead of using the spinning ones. Qwen3.5-2B Q4_K_M on an AMD EPYC VM with 10 vCPUs: 46 to 55 tokens/s before, 65 after (llama.cpp 63 to 76 on the same, busy machine).
- CUDA: 16 simultaneous users (or a few at long contexts) failed with "illegal memory access": an attention call staged its lengths, then grew the metadata ring for its block tables and freed the memory the lengths were in. Found and verified on a Colab L4 (16 of 16 requests answered afterwards).
- Models with recurrent layers (Qwen3.5, Mamba) on a GPU: the memory plan now leaves room for the recurrent states of all sequences; before, the KV pool took the whole card and a busy step ran out of memory.
- A model step that failed (for example a device error under load) stopped the whole server; now its requests get the error, the error is logged at once, and the server keeps serving (three failed steps in a row still stop it).
- Gemma 4 on the CPU: the fast attention kernel now takes the sliding window and the score scale, so the model no longer uses the scalar reference in every layer (Core Ultra 5 235U, Gemma 4 E4B Q4_K_M: prompts 34 instead of 18 tokens/s, answers up to 8.7 instead of 3 to 4).
- Gemma per-layer weights stored as bf16 or f16 now go to the device as Q8_0 as well (the projection of the per-layer inputs ran in the slow bf16 kernel).
- An explicitly chosen device that cannot run a model (for example Gemma 3n on Vulkan) no longer stops the server: the model runs on the CPU and the reason is logged.
- Gemma 4 on Vulkan and the NPU failed with "rope width 512 invalid for head width 256": the device pass used one rotary width for all layers.
- Windows: the low-power efficiency cores of Intel Core Ultra are told from the other efficiency cores by their cache (Windows gives them the same efficiency class), so `--threads auto` picks 8 instead of 9 threads on a Core Ultra 5 235U; an explicit `--threads n` gets the same core placement as the automatic count (a 10-thread run answered at 9 tokens/s without it, 24 with it).
- The code page sent `reasoning_effort: high` whenever thinking was on; it now sends what the loaded model understands for the chosen level.
- KV block copies (several choices per request, swap preemption) work with KV pools whose layers have their own sizes.
